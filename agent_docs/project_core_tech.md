# Project Core Technology

- **Client:** Phaser `4.2.1`, TypeScript, and Vite. `src/main.ts` creates the Phaser game and registers ten scenes, including Campaign; the scene size comes from `src/game/maps/map1.ts`. Classic Siege and Campaign share the fixed-step `GameScene`; campaign content and run state are isolated in `src/game/campaign/`.
- **Backend:** Cloudflare Worker in `worker/index.ts`, with a D1 binding named `DB`. The client API module is `src/api/leaderboardClient.ts`; shared types and score validation live in `src/shared/`.
- **Local development:** `npm run dev` starts Vite; `/api` requests proxy to `http://localhost:8787`.
- **Build and checks:** `npm run build` runs `tsc -b` then `vite build`; `npm test` runs Vitest. These commands are available, but their presence does not indicate a passing run.
- **Deployment:** `wrangler.toml` points to `worker/index.ts`, serves static assets from generated `dist/`, and configures D1 migrations from `migrations/`.

Campaign progression uses local `CampaignRepository` storage under `aetherhold-campaign-v1` and version-1 account/cloud records through the Worker. Local and Worker validators accept canonical level keys 1–100; campaign results do not enter Classic score or best-run systems. Cloud writes use compare-and-swap monotone merge, and an incompatible stored row is preserved. No D1 schema migration was needed. Rollback must retain a Worker compatible with expanded v1 records; older clients may reject new-level responses and need a reload. See `docs/CAMPAIGN_WORLDS_4_10.md`.

`src/game/ui/ViewportMask.ts` provides the shared screen-space viewport-mask controller for Campaign route nodes, the Game battlefield, and Leaderboard rows. Phaser 4 uses the external WebGL mask when available, with a Canvas GeometryMask fallback; resize rebuilds or refreshes the mask, and scene shutdown disposes its resources. Campaign route pointer actions also check viewport bounds, preventing hidden nodes from receiving input. The Codex measures wrapped boss-description height before positioning following content. P6 tests cover WebGL refresh, Canvas cleanup, clipped-pointer rejection and measured text layout.

Campaign art is gated by manifest state and the exact approved-path allowlist. The cold main menu does not load campaign art; campaign entry requests assets allowed by the current manifest. The manifest contains 124 active final assets: 43 original files, 77 accepted World 4–10 v2 files, and four Sentinel/Cinder campaign-tier cosmetics. The 77 v1 expansion rollback files remain hash-pinned; no expansion asset is provisional or `final_required`. Gameplay requests the selected approved map plate and visual-tier tower files. The battlefield renderer composites terrain with runtime geometry and retains a deterministic painter fallback; missing enemy/boss atlases use procedural textures. A failed approved request holds in Preload and offers Retry/Back. See `docs/CAMPAIGN_PRODUCTION_ASSETS.md` for campaign asset evidence and `docs/SENTINEL_CINDER_ART_PROVENANCE.md` for the new tower art.

Sentinel and Cinder use dedicated four-frame 627×627-cell foundation sheets and 192×192 campaign tiers. Shared `towerArt.ts` rendering uses measured per-stage bounds, ground insets, centers, and weapon origins from `additionalTowerGeometry.ts`; previews, placed towers, portraits, and result miniatures share this renderer. Runtime loads WebP, while packaged PNGs and the accepted full-size sources are retained. The campaign manifest requests the selected cosmetic tier, and tower-specific projectile and impact visuals leave combat data unchanged. See `docs/SENTINEL_CINDER_ART_PROVENANCE.md` for generation prompts, geometry, source paths, and review evidence.

Expansion levels use longer 32–52-wave schedules; levels 1–40 remain unchanged. The simulated-duration range and its wall-clock limits are recorded in `docs/CAMPAIGN_WORLDS_4_10.md`. Speed selection and pauses affect player wall-clock duration. Current deployment evidence belongs in `agent_docs/project_progress.md` and `agent_docs/latest_session_work.md`.

Keep gameplay rules and balancing values in `src/game/systems/` and `src/game/config/`. Keep cloud and database access in the API/Worker boundary, outside Phaser gameplay systems, as required by `docs/SPEC.md` and `docs/AI_AGENT_INSTRUCTIONS.md`.
